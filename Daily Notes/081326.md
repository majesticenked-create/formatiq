**Issues:**
- **[Medium] Check 5 — `verdicts.jsonl` is malformed and its data is useless.** Two separate bugs in `log-stop-verdict.sh`:
  1. `jq -n` (line 39) is called without `-c`, so every append writes pretty-printed multi-line JSON into a file that must be one-object-per-line to qualify as JSONL. All 123 recorded verdicts are concatenated multi-line blobs — any standard JSONL/line-based parser (including a plain `jq -c` read) fails on this file as-is.
  2. Independent of the format bug: **100% of all 123 records have `decision: "unknown"` and `task_type: "other"`** — the Stop hook's haiku-model quality classification has apparently never produced a real verdict, across every session logged. I isolated the sed/jq extraction logic in `log-stop-verdict.sh` and confirmed it correctly parses a clean single-line `{"decision":"allow",...}` string when tested directly — so the bug isn't in that extraction regex itself. The consistent 100% failure rate across every session instead points to the actual stdin the hook receives at Stop time not matching the bare JSON shape the extraction assumes (most likely wrapped in the harness's hook-payload envelope rather than being the model's raw text directly) — this needs a live capture of `$RAW_VERDICT` on the next real Stop-hook firing to confirm the exact shape and fix the extraction accordingly.
  - Net effect: the "quality gate at >=2 blocks per session" feature described in the hook's own header comment cannot currently trigger, since `decision` never evaluates to `"block"`. This gate has silently never functioned.
